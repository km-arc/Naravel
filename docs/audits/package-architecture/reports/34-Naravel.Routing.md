## Executive assessment

The package provides named routes, route groups, middleware aliases, route model binding, resource routes, throttling and signed URL validation. The throttle breaker has been updated to measure its short failure period using a monotonic timestamp, so system-clock changes do not shorten or extend that breaker period.

Two signed-URL issues remain. Link generation signs a relative route path without the current request's PathBase, but validation includes PathBase; applications hosted under a path prefix can therefore reject links generated by the same application. Separately, signed URL expiry validation reads DateTimeOffset.UtcNow directly instead of using the injected TimeProvider required by the repository's time-dependent code rule.

## Findings

### [P2] ROU-001 — Signed URLs can fail validation when the application uses PathBase

- Remediation state: OPEN.
- Evidence status: SEEN IN SOURCE; PathBase end-to-end test NOT RUN.
- Evidence: SignedRoute in src/Naravel.Routing/Url/UrlGenerator.cs calls Route(name, values), which uses LinkGenerator.GetPathByName without an HttpContext. SignedUrlService.Sign signs the path returned by that call. SignedUrlService.IsValid instead builds the path using context.Request.PathBase.Add(context.Request.Path). Existing signed URL tests cover valid, tampered and expired requests but do not host the app under a PathBase.
- In everyday words: The URL creator signs one path, but the checker later includes the application's extra path prefix. The paths no longer match, so the application can reject a link it just created.
- Realistic example: The application is mounted under /app. The named route itself is /download. SignedRoute signs /download, but a request reaches the application with PathBase /app and Path /download. Validation checks /app/download and returns 403.
- Why the evidence proves the risk: the signing and validation paths are built from different inputs. The signature protects the canonical path, so adding a prefix only during validation changes the value being compared.
- What is not proven: this was established by tracing the two source paths; no TestServer or reverse-proxy PathBase reproduction was run.
- Required safe outcome: URL creation and validation must use the same canonical path, including the configured application prefix when the link will be served under one.
- Regression tests required: host the test application under a non-empty PathBase; generate a normal and temporary signed route; prove both are accepted. Then alter the prefix/path/query and prove the request is rejected. Keep existing tampered and expired tests.
- Public API / PDR / release impact: signed URL compatibility for applications hosted below a URL prefix; no public API change expected.

### [P2] ROU-002 — Signed URL expiry uses the system clock directly

- Remediation state: OPEN.
- Architecture disposition: repository time-dependent code rule requires injected TimeProvider for clock decisions.
- Evidence status: SEEN IN SOURCE; clock-step reproduction NOT RUN.
- Evidence: IsValid in src/Naravel.Routing/Url/SignedUrlService.cs compares the expiry timestamp with DateTimeOffset.UtcNow.ToUnixTimeSeconds(). The service constructor receives IDataProtectionProvider only and does not receive TimeProvider. The repository rule in AGENTS.md requires injected TimeProvider for application/runtime time decisions. Existing tests create an already-expired link using DateTimeOffset.UtcNow but do not control the validation clock.
- In everyday words: A temporary link checks the computer's clock directly. If that clock is moved forward or backward, the link may expire too early or remain valid longer than its expiry time.
- Realistic example: A temporary download link should expire at 14:00. If the host clock is moved backward, the check can still think it is before 14:00 and accept the link beyond its intended expiry.
- Why the evidence proves the gap: the expiry decision reads global system time, so it cannot be controlled by the application's clock abstraction or deterministic test clock.
- What is not proven: source inspection confirms the direct clock read; no system-clock step or manual TimeProvider test was run.
- Required safe outcome: use an injected TimeProvider consistently for signed URL expiry, while retaining UTC timestamp semantics across instances.
- Regression tests required: manually set the validation clock before, at and after expiry; verify acceptance only before the expiry instant. Also prove that changing the system wall clock independently does not change the injected clock's decision.
- Public API / PDR / release impact: internal dependency injection change; no public URL format change should be necessary.

## Plain-language explanation

Routing can create and check signed links. A link's path is part of what gets signed. The code that creates a link omits the host application's PathBase, while the code that checks it includes that prefix. A site hosted under /app can therefore reject its own valid link. The expiry check also reads the computer clock directly, so time changes can affect when a temporary link expires. Both issues were found by reading source; neither was reproduced in a running host in this audit.
